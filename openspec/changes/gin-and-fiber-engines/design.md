# Design

## Context

Builds on `core-server`, archived 2026-11-17 with its specs synced to `openspec/specs` (see proposal.md - Impact for the assumptions, re-checked at consolidation). The net/http engine works and its engine-neutral logic (state machine, config resolution, trace parsing, logging pipeline, access and triage record builders) lives in unexported identifiers of package `srvr` and in `internal/tracectx`. Go's `internal` rule is path-based, so a nested module such as `srvr/ginsrvr` can technically import `srvr/internal/...` (consolidation probe), but internal packages carry no compatibility promise across separately versioned modules, so the plan keeps a public, marked `engine` package (D1).

During its four verification passes `core-server` grew guards for faulty consumer code (listed in D10) that every engine must reuse, not re-implement.

Adapter facts re-checked at consolidation (prblm `v0.1.0`, ginprblm `v0.1.0`, fiberprblm `v0.1.0`, gin `v1.12.0`, fiber `v3.7.0` on fasthttp `v1.78.0`, all still the latest releases): `ginprblm.Middleware(opts...)` and `ginprblm.Recovery(opts...)` each build their own `prblm.Handler` (so each panics on invalid options, which srvr validates first); `fiberprblm.ErrorHandler(opts...)` builds one, while `fiberprblm.Recovery()` takes no options and returns the panic as an error for the error handler to render. Both adapters wrap a recovered panic in their own unexported type that unwraps to `*prblm.PanicError` (`ginprblm` `panickedError`, `fiberprblm` `recoveredError`), and both turn a panic inside `prblm.Handler.Respond` into a bodiless `500`. `fiberprblm.ErrorHandler` calls `errors.AsType[*fiber.Error]` and `errors.Is` on the error it receives. gin's own `c.Error(err)` calls `errors.As` on the consumer's error before srvr sees it.

Engine facts that shape the approach:
- Gin v1.12.0: `*gin.Engine` is an `http.Handler`; routes match by `c.FullPath()`; `HandleMethodNotAllowed` is off by default; `ContextWithFallback` is off by default; `gin.Default()` installs its own logger and recovery; route conflicts panic. The mode is process-global (`mode.go` `ginMode`), and in debug mode `gin.New()` and every route registration print `[GIN-debug]` lines to `gin.DefaultWriter` (stdout); `DebugPrintRouteFunc` is a package variable, not per engine. `gin.New()` trusts every proxy (`0.0.0.0/0`, `::/0`) and redirects trailing slashes (`RedirectTrailingSlash`). With `HandleMethodNotAllowed`, gin sets `Allow` itself, in the order method trees were created (`gin.go:738-753`), and runs global middleware for 404/405. ginprblm's `Middleware` must be registered before middleware that aborts or writes; `ginprblm.Recovery` replaces `gin.Recovery`.
- Fiber v3.7.0 on fasthttp: handlers `func(fiber.Ctx) error`; `fiber.Ctx` is pooled and its strings and byte slices are reused after the handler returns; it implements `context.Context` but never cancels; `c.Route()` inside middleware is the middleware itself, and after `c.Next()` it is the matched route only when `c.Matched()` is true (otherwise the last middleware's own route, `/` or a group prefix); `Config.ErrorHandler` receives returned errors only after the whole chain has returned (`router.go:1052-1056`), so middleware sees status `200` unless it calls the error handler itself, as fiber's logger does (`middleware/logger/logger.go:137-146`); protocol-level rejections (413, 431, 408) replay the `Use` chain with a nil chain error and a pre-seeded status, then call the error handler (`app.go:1847-1877`); `ShutdownWithContext` closes idle keep-alive connections (fasthttp v1.78.0 `closeIdleConns` in its wait loop, despite fiber's godoc) but stops waiting at the deadline and leaves active connections open; `BodyLimit <= 0` means 4 MiB; the header limit is `ReadBufferSize` (8 KiB) and fasthttp has no header-read timeout; prefork and the startup message live in `ListenConfig`, not `fiber.Config`; `app.Test` returns a transport error, not a response, for protocol-level rejections; `app.Listener(ln)` serves on a consumer listener; `app.Test` drives tests.
- prblm adapters build their own handler from `...prblm.Option`; srvr already keeps one shared option list per server.

## Goals / Non-Goals

**Goals:**
- Gin and Fiber engines with the same lifecycle, config, problems and logs as net/http, using one shared implementation of everything engine-neutral.
- A parity suite that fails when any engine drifts.

**Non-Goals:**
- An engine plug-in interface for third parties. The engine-support package is public only because Go modules need it; it is documented as being for srvr's own engines and may change before v1.
- Metrics, tracing, scrty, debug buffering (later changes).
- Fiber prefork, Gin H2C (rejected at construction / not exposed).

## Slices

1. **Engine-support extraction** (refactor, no behaviour change): move the engine-neutral pieces the Gin engine needs from core internals into `github.com/kartaladev/srvr/engine` (lifecycle state machine with `Serve`/`Drain` callbacks, resolved config, trace context middleware primitives, the per-request holder as `engine.RequestState` (D7), access/triage record builders, log pipeline), and make the net/http engine use them. Satisfies engine-support (Engines share one configuration model; The engine-support API is marked as such) for net/http. Hot paths: unchanged net/http request pipeline, now through the shared builders. The whole `core-server` test suite stays green; only what Gin needs is moved.
2. **Gin engine end to end**: `ginsrvr.New`, `Register`, `Start`/`Shutdown` over an `http.Server` with the gin engine as handler, srvr middleware outermost (trace, access, ginprblm middleware, ginprblm recovery), `ContextWithFallback`, `HandleMethodNotAllowed`, `RedirectTrailingSlash` off, sorted `Allow`, 404/405 problems logged as failed, body limit middleware, the `server.config.warning` event (D9) with the `gin_debug_mode` warning, `WithEngine` hook with re-asserted safety settings. Satisfies gin-engine (all), engine-support (Engines share one lifecycle state machine) for gin. Hot paths: gin pipeline, `c.FullPath()` route capture, error collection from `c.Errors`, recovery.
3. **Fiber engine end to end**: extract whatever extra engine-neutral piece Fiber needs (expected: a listener-driven serve/drain adapter), then `fibersrvr.New`, `Register`, Fiber app with derived config, `app.Listener`, srvr middleware (trace into `c.Context()`, access record reading the matched route after `c.Next()`, fiberprblm recovery), fiberprblm error handler invoked from the access middleware, forced close of lingering connections, srvr-owned `ListenConfig` (no prefork), `WithFiberConfig`, `ReadBufferSize` derived from `MaxHeaderBytes` and capped, duplicate-route detection. Satisfies fiber-engine (all), engine-support lifecycle rows for fiber. Hot paths: fiber pipeline, value copying, route capture, error handler, drain and forced close.
4. **Parity suite**: `internal/paritytest` module (test-only, not released) running one Examples table per scenario against all three engines, plus exception pins. Satisfies engine-parity (all). Hot paths: none new; it guards the three pipelines.
5. **Route listing and route checks** (D8): `engine.Routes` built on every engine after the configure phase and passed to `srvr.WithRouteCheck` checks before binding. Satisfies engine-support (Registered routes are listed with their configurer). Useful on its own (a consumer can assert its route table at startup) and the input scrty-integration's collision check needs. Hot paths: route attribution per configurer, implicit-route filtering, check invocation under recover.

## Decisions

### D1. Public `engine` package in the core module for shared pieces
Engine modules are separate Go modules and cannot import the core's `internal/` packages. The shared pieces move to `github.com/kartaladev/srvr/engine`, documented "for srvr engine implementations; API may change before v1". Alternative: duplicate the logic per engine - rejected, parity would rot; alternative: one module containing all engines - rejected by the module-layout decision (consumers must not download gin and fiber together).
**Failure modes:** consumers start depending on `engine` - godoc warning plus no stability promise before v1; extraction changes net/http behaviour - slice 1 is a pure refactor gated by the full `core-server` suite, the log golden test and the problem tests.
**Layering (pending owner decision, consolidation 2026-11-17):** `srvr.WithRouteCheck(func(context.Context, engine.Routes) error)` makes `srvr` import `engine`, so `engine` cannot import `srvr`. `engine` must still resolve `srvr.Option` values (engine-support "Engines share one configuration model") and return `srvr.ErrConfig`. The plan does not say where the public configuration types, `Option`, `Trace` and the sentinel errors are then defined; the options are recorded in notes.md ("Where srvr's public configuration types live once engine exists"). Slice 2 starts after that decision.

### D2. Gin runs inside srvr's `http.Server`
`ginsrvr` builds `gin.New()` (never `gin.Default()`), leaves gin's global mode alone (srvr never calls `gin.SetMode`; gin has no per-engine mode - documented), and serves it through the same `http.Server` and lifecycle as net/http, so timeouts, header limit, drain and forced close are inherited. The body limit is not: in the core it is `http.MaxBytesReader` middleware, so ginsrvr installs the same shared middleware (from `engine`) on the gin engine, and a read error reported with `c.Error` renders `413` through the shared prblm options. Pipeline order on the engine: srvr trace -> srvr access -> `ginprblm.Middleware` -> `ginprblm.Recovery` -> consumer groups. 404/405: gin records the status (and sets `Allow` for 405) and runs the global middleware, where `ginprblm.Middleware` turns the recorded status into a problem, keeping `Allow`; no `NoRoute`/`NoMethod` handler is needed. Trusted proxies are set to none before `WithEngine` runs. `RedirectTrailingSlash` is turned off (gin answers `GET /users/` with an HTML `301` otherwise) and re-asserted after the hook. `Allow` is rewritten sorted by the access stage before the problem is rendered, because gin orders it by method-tree creation (`gin.go:738-753`). A request with no matched route (`c.FullPath()` empty and status 404 or 405) is marked failed in the request state even though `c.Errors` is empty, so it logs `http.request.failed` like net/http and fiber. When `gin.IsDebugging()` at construction, srvr writes one `gin_debug_mode` config warning (D9) instead of touching gin's globals. `ginprblm.Recovery` passes a panic with `http.ErrAbortHandler` on (`ginprblm/recovery.go:58`); srvr's access stage observes it in a deferred recover, writes the aborted-request record (`http.request.failed`, `WARN`, `error.kind`/`error.type` `panic`, `srvr.response.aborted` `true`, no `problem`) and re-raises it so net/http aborts the connection, exactly as on net/http.
**Failure modes:** `gin.SetMode` is global - not touched; in debug mode gin prints `[GIN-debug]` lines to stdout and srvr cannot silence them per engine - documented and reported once as the `gin_debug_mode` warning; ginprblm calls the `OnError` hook also for `c.AbortWithStatus(4xx)` with an unexported error - srvr classifies a request as failed from `c.Errors` and recovered panics, never from hook calls alone; a `WithEngine` hook that calls `Use` or registers routes would put them outside srvr's pipeline - srvr compares `e.Handlers` and `e.Routes()` before and after the hook and rejects any addition; ginprblm registered after an aborting middleware - impossible, srvr installs it before any consumer group; `c.Error` after the body was written - kept as committed (parity exception).

### D3. Fiber runs its own fasthttp server on srvr's listener
srvr binds the listener (same `Addr`/`WithListener` rules), passes it to `app.Listener`, and runs the shared state machine around it. Fiber config is derived from srvr config, then `WithFiberConfig` runs, then srvr re-asserts `ErrorHandler`. srvr builds the `ListenConfig` itself (startup message off, prefork off; `app.Listener` ignores prefork for custom listeners, `listen.go:471-473`) and never exposes it. `MaxRequestBodyBytes` `-1` maps to `math.MaxInt`, never to `BodyLimit` `-1`. `ReadBufferSize` is `min(MaxHeaderBytes, 65536)`: fasthttp allocates it per connection, so the 1 MiB default would cost 1 GiB at 1000 connections; capping a consumer-set value writes a `fiber_header_limit_capped` warning, capping the default does not. fasthttp has no header-only timeout, so `ReadHeaderTimeout` is not mapped (parity exception) and `ReadTimeout` bounds header and body together. After the configure phase srvr reads `app.GetRoutes(true)`, normalises parameter names (`:id` and `:name` both become `:`) and fails `Start` with `srvr.ErrRouteConfig` on a duplicate method and pattern, because fiber registers duplicates silently and the first wins. Unknown methods (`FOO`) are answered by fiber with a plain `501` before any middleware; srvr accepts this as a parity exception rather than listing methods in `RequestMethods`. Shutdown calls `app.ShutdownWithContext(ctx)`; on deadline srvr closes the listener-tracked connections itself (connection tracking through a wrapping `net.Listener`) and cancels a per-server base context that every request context derives from.
Shutdown hooks (`srvr.WithShutdownHook`) are run by the shared lifecycle state machine in `engine`, so gin and fiber get net/http's order and stop paths for free: `BeforeDrain` before `ShutdownWithContext` (fiber) or `http.Server.Shutdown` (gin), `AfterDrain` after the drain adapter returns, including the forced-close path.
**Failure modes:** `ShutdownWithContext` on an app that never served returns `nil` (fasthttp has no listener, `server.go:2212`), and one that races `Serve` before fasthttp registered the listener closes nothing (`app.go:1427-1431`) - srvr closes its own listener and waits for `Listener` to return; active connections stay open past the deadline - closed by the tracking listener; fasthttp read timeout zero keeps idle connections - srvr always sets timeouts from config (negative disables only on explicit opt-in).

### D4. Fiber values are copied at the boundary
The access middleware copies method, route, status, user agent and any header it logs into Go-owned strings (`strings.Clone`) before `c.Next()` returns control; trace ids are generated as Go strings; error text is produced from the error value, not from Fiber buffers. Route is read after `c.Next()` from `c.Route().Path` only when `c.Matched()` is true; otherwise `http.route` is omitted. When the chain returns an error, the access middleware calls the app's error handler itself and returns nil, so the record has the status the client gets; an unmatched request with a nil chain error and a status of 400 or more is a protocol-level rejection and is recorded as failed. Protocol rejections (`408`, `413`, `431`) come from fasthttp before routing: fiber's `serverErrorHandler` seeds the status, replays only the `Use` chain (route handlers skipped, the chain returns nil, `router.go:763`) and then calls `app.ErrorHandler` itself (`app.go:1847-1877`). srvr's access stage recognises the replay by a status of 400 or more already set when the stage starts (a normal request starts at `200`), does not render, and builds the record's `problem` group from that status and `http.StatusText`; fiber's following error-handler call renders the client's problem, and srvr's `OnError` then finds no request state and only skips. A panic with `http.ErrAbortHandler` is recovered by `fiberprblm` like any panic (`fiberprblm/recovery.go:23`): srvr never re-raises on fiber because fasthttp does not recover panics and the process would crash - parity exception.
**Failure modes:** a copy missed - the concurrent context-reuse test with 1000 requests across routes catches cross-request leaks under `-race`; middleware-scoped route returned (`/` or the group prefix for 404/405) - tested by the "behind group middleware" rows; the error handler run twice (by srvr and by fiber) - srvr returns nil after rendering, tested by counting `OnError` calls.

### D5. Fiber request context
srvr creates a request context from the server's base context, stores trace and logger in it, and sets it with `c.SetContext(ctx)`; `TraceFromContext` and `LoggerFromContext` accept any `context.Context` and, when given a `fiber.Ctx`, fall back to `c.Context()`. Accessors in the core use only `context.Context`, so no fiber import enters the core.
**Failure modes:** handlers that pass `c` to long-running work - documented: use `c.Context()`; per-request cancel functions leak - released in the access middleware's defer.

### D6. Parity suite as a test-only module
`internal/paritytest` has its own `go.mod` requiring all three engine modules, is listed in `go.work`, and is never released. Each parity scenario is one table, rows per engine, with exceptions pinned as separate tests.
**Failure modes:** parity drift hidden by a too-loose comparison - bodies compared as exact JSON after decoding, key sets compared exactly, only listed fields excluded.

### D7. One per-request holder: `engine.RequestState`
Core D5's route holder, the trace context, the failure flag and the status the client got live in one struct, `engine.RequestState`, created by the outermost srvr stage and fetched with `engine.StateFrom(ctx)` (nil and false outside srvr's pipeline). Engines write the matched route, matched flag and status into it; recovery and error rendering write the failure. Later changes extend this struct rather than adding holders: otel-observability its trace source, scrty-integration the resolved client address and principal. Fields are added by the change that first writes them (Gall's Law), always to this one struct. On fiber the access stage is srvr's only caller of the error handler, for handler and route errors (D4); fiber itself calls it for protocol rejections it detects before routing (`408`, `413`, `431`), after the replayed chain has returned, and the access stage records those from the pre-set status without rendering. Later stages read the failure from the state, never from the chain's returned error, which is nil once rendered.
**Failure modes:** a stage reading state outside srvr's pipeline - `StateFrom` returns false and the stage skips; concurrent goroutines spawned by a handler - fields written only by srvr's stages on the request goroutine, documented; fiber context reuse - the state is allocated per request and referenced only through the request context srvr created (D5), never from `fiber.Ctx` locals.

### D8. Route listing with configurer attribution, and route checks
During the configure phase srvr records which configurer declared each route: the net/http registrar records patterns directly; gin and fiber diff the engine's route table (`e.Routes()`, `app.GetRoutes(true)`) before and after each `Configure`. Each entry is `engine.Route{Method, Pattern, Configurer}`, pattern in the engine's own syntax, configurer named with `%T`. Middleware (`Use`) entries, including a path-scoped fiber `Use("/assets", ...)`, and routes an engine adds implicitly (fiber's automatic `HEAD` for `GET`) are excluded, so the list is what the consumer declared. A route served for every method is listed once with `Method` `""`: a net/http method-less pattern or `Mount` (pattern as registered, `/static/` for `Mount("/")` in group `/static`), and on gin and fiber a pattern one configurer registered for the engine's whole any-method set (`Any`, `All`, or the same methods by hand). `srvr.WithRouteCheck(func(context.Context, engine.Routes) error)` checks run, in order and under recover, after the configure phase and before binding, each with `Start`'s context and its own copy of the listing; an error or panic fails `Start` with `srvr.ErrRouteConfig`, and `Start`'s context ending fails it with the context error. Fiber's duplicate detection (D3) is the first internal check.
**Failure modes:** a configurer that registers a route in another configurer's group - attributed to the configurer that was running; fiber's implicit `HEAD` identification differs between versions - pinned by the fiber listing row, re-checked at each consolidation; a check that blocks - it receives `Start`'s context; when that context ends `Start` returns the context error and abandons a check that ignores it (documented); a check that mutates its input - each check gets a copy; a path-scoped fiber `Use` that serves files is invisible to route checks - documented in `fibersrvr` godoc and to scrty-integration's shadowing check; nil check - construction error.

### D9. Configuration warnings
A working but likely unintended configuration is reported as one `WARN` record, `msg` `server.config.warning`, with `srvr.warning.code` (stable snake_case, part of the log schema) and `srvr.warning.message`. Engine settings warn at construction; route-dependent warnings (used by scrty-integration) warn at `Start`. Warnings never fail. Codes in this change: `gin_debug_mode`, `fiber_header_limit_capped`. Adding codes or this event is additive and keeps `srvr.log.schema`.
**Failure modes:** a warning repeated per request - only construction and `Start` emit; the logger failing - same handling as other lifecycle records.

### D10. Engines reuse the core's guards
Every guard `core-server` added for faulty consumer code moves to `engine` with the rest of the shared pieces and is the only implementation; engine modules call it and never format, unwrap or lock on their own:
- Text of consumer values (`errorText`, `valueText`, `guardedError`) for every configurer, engine-hook, route-check and listener failure and every panic value; an engine module never calls `Error()`, `String()` or `fmt` on a consumer value directly.
- `guardChain` before any prblm resolution. On fiber the access stage is the only caller of the error handler (D4/D7) and passes the guarded error, because `fiberprblm.ErrorHandler` calls `errors.AsType` and `errors.Is` itself. On gin a srvr stage between `ginprblm.Middleware` and the consumer groups replaces each `c.Errors[i].Err` with its guarded value after `c.Next()` returns (nothing to do when `c.Errors` is empty), so ginprblm never resolves a cyclic chain that reached `c.Errors` by assignment; a chain passed to `c.Error` hangs in gin first (notes.md, open decision).
- Failure classification reads a panic through `errors.As` to `*prblm.PanicError`, because both adapters hand srvr's `OnError` their own wrapper type rather than the `*prblm.PanicError` the net/http path sees; a type switch on the error itself would log a panic as a returned error. The cycle check, the chain walk and the panic check share one bounded walk per failed request; successful requests pay nothing.
- `guardedListener` wraps every listener srvr serves on: gin through the shared `http.Server` path, fiber below its connection-tracking listener, so `app.Listener`'s `Accept` panics become errors and every `Close` (fasthttp's, the tracker's, srvr's) returns nil and runs the consumer's `Close` once. `listenerAddr` validates the address on every engine.
- `engine.Lifecycle` holds its lock only to read and move state; it calls `Serve`, `Drain`, configurers, engine hooks, route checks, shutdown hooks and log handlers with no lock held, so consumer code may call `Addr`, `Register`, `Ready` or `Shutdown` on its own server.
- Lifecycle and route-check failure text goes through `exceptionMessage` (redactor, `[redaction failed]`, 8 KiB cap); request failures through the shared access and triage builders, so failed records are never suppressed on any engine.
- One log handler implementation (panicking `Enabled`/`WithAttrs`/`WithGroup`/`Handle` counted and skipped) and one process-wide `LogWriteErrors` counter, which `srvr.LogWriteErrors` reports for every engine.
**Failure modes:** an engine adds its own formatting of a consumer value - review rule plus the engine-support "Consumer faults on every engine" rows per engine; a guard moved with a behaviour change - slice 2 keeps the `core-server` suite green; gin's `c.Error` loop - out of srvr's reach, pending decision.

## Defaults

| Behaviour | Default | Why | Override |
|-----------|---------|-----|----------|
| Core settings (address, timeouts, limits, logs, trace) | same as `core-server` | one behaviour across engines | same options and config structs |
| Gin mode | gin's global mode untouched (debug unless `GIN_MODE` or `gin.SetMode`); one `gin_debug_mode` warning at construction in debug mode | srvr must not change process-global state, but the consumer must learn why `[GIN-debug]` lines appear | consumer sets `GIN_MODE=release` or `gin.SetMode` |
| Gin `RedirectTrailingSlash` | off, re-asserted | an HTML `301` is not a problem; net/http answers `404` | none (parity setting) |
| Gin `Allow` order | sorted | identical to net/http | none |
| Gin body limit | `http.MaxBytesReader` at `MaxRequestBodyBytes` | gin does not inherit it from `http.Server` | srvr `Config` |
| Gin `ContextWithFallback`, `HandleMethodNotAllowed` | on, re-asserted | trace in `c`, correct 405 | none (correctness settings) |
| Gin trusted proxies | none, set before the hook (gin's own default trusts all) | client IP not spoofable | `WithEngine` calling `SetTrustedProxies` (loosening) |
| Gin logger / recovery | not installed | srvr owns both | none |
| Fiber `ErrorHandler` | fiberprblm's, re-asserted | one problem format | `WithProblemOptions`, `WithErrorHook` |
| Fiber `BodyLimit`, timeouts | from srvr `Config`; `ReadHeaderTimeout` not mapped (no fasthttp equivalent) | one config surface | srvr `Config` |
| Fiber `ReadBufferSize` | `min(MaxHeaderBytes, 65536)` | header limit without a per-connection 1 MiB allocation | `WithMaxHeaderBytes` up to the cap |
| Fiber duplicate routes | fail `Start` | fiber accepts them silently and the first wins | none |
| Fiber `Immutable` | off; srvr copies what it keeps | performance; safety does not depend on it | `WithFiberConfig` |
| Fiber prefork | never enabled; `ListenConfig` owned by srvr | breaks lifecycle | none |
| Fiber proxy header | off | client IP not spoofable | `WithFiberConfig` (loosening) |

## Hot Paths

- Gin: srvr trace and access middleware, body-limit middleware, ginprblm middleware and recovery, unmatched 404/405 classification and `Allow` sorting, `c.FullPath()` capture, `c.Errors` to triage record.
- Fiber: srvr trace (context creation and `SetContext`), access middleware with value copying, post-`Next` matched-route read and error-handler call, protocol-rejection replay, fiberprblm recovery and error handler, not-found and method-not-allowed paths, listener tracking and forced close, `ReadBufferSize` derivation, duplicate-route detection.
- Shared: lifecycle state machine through both serve/drain adapters, config resolution, `engine.RequestState`, record builders, route listing and route checks, config warnings.
- Error branches: configurer panic per engine, route conflict panic per engine, nil handlers, hook panics (`WithEngine`, `WithFiberConfig`), drain deadline per engine, panics with `http.ErrAbortHandler` on gin, and every engine-support "Consumer faults on every engine" row (hostile values, cyclic chains, panicking log handlers and redactors, faulty listeners, re-entrant calls from consumer code).

## Risks / Trade-offs

- [Public `engine` package becomes de-facto API] -> explicit godoc warning; carry-over to revisit before v1.
- [Gin and Fiber versions move under us] -> engine modules pin minor versions; each change's consolidation group re-checks; parity suite runs in CI.
- [fasthttp does not detect client disconnects] -> documented parity exception; handlers needing it are told to use net/http or gin.
- [Gin `Allow` lacks `HEAD` (gin does not route `HEAD` to `GET` handlers); fiber unknown methods get a plain `501`; fiber header limit capped at 64 KiB and no header timeout] -> parity exceptions pinned by tests and godoc.
- [The route listing depends on gin's and fiber's route-table APIs] -> listing rows per engine; re-checked at each consolidation.
- [Two adapters (ginprblm, fiberprblm) render problems independently] -> parity suite compares exact bodies; prblm's own parity suite is an upstream guard.

## Migration Plan

Additive. Release `v0.2.0` of the core (new `engine` package, `srvr.WithRouteCheck`, the `server.config.warning` event - additive, `srvr.log.schema` unchanged) together with `ginsrvr/v0.1.0` and `fibersrvr/v0.1.0`. The net/http engine's behaviour is unchanged; consumers of `core-server` need no changes.
