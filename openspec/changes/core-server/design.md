# Design

## Context

Greenfield repository; see proposal.md - Why. Constraints that shape the approach:
- Go 1.27, `net/http.ServeMux` with method and wildcard patterns (`r.Pattern` is set after routing).
- prblm v0.1.x: `NewHandler(opts...)` panics on an invalid option; `Wrap`, `Write`, `Recover` work on net/http; `OnError` replaces any earlier hook (single slot); enrichers can set extension members; `RequestFrom(ctx)` is available in hooks; the default `instance` enricher uses the path without query. prblm never logs.
- ServeMux answers unmatched paths (404) and wrong methods (405 + `Allow`, e.g. `GET, HEAD, POST`) itself, in plain text, and panics on conflicting registrations. `mux.Handler(r)` does not set `r.Pattern` or path values; only `mux.ServeHTTP` does, on the request it receives.
- Later changes (gin, fiber, otel, scrty) reuse what this change builds; anything engine-neutral must not import net/http-only details into its API.

## Goals / Non-Goals

**Goals:**
- One engine (net/http) end to end, with the engine-neutral pieces (lifecycle, trace context, logging, triage records, prblm wiring) shaped so the gin and fiber engines can reuse them.
- Every behaviour has a default and an override, programmatic and by config struct.

**Non-Goals:**
- An engine abstraction interface. Engines are added in the next change; extracting the shared shape before a second engine exists would be building ahead of need. This change keeps engine-neutral code in internal packages that the next change can lift.
- Metrics, tracing spans, OpenTelemetry - next-but-one change.
- TLS, h2c, health endpoints, stack capture at error creation (carry-overs, `unassigned`).

## Slices

1. **Minimal server** (starts with the module scaffolding it needs): `New`, `Register`, `*Group` with `GET/POST/...` and error-returning handlers, `Start(ctx)` blocking until cancel, `Shutdown`, `Ready`, `Addr`; a handler error rendered by prblm as a 500/404 problem. Satisfies server-lifecycle (Start serves until its context ends; Readiness is observable), route-registration (Route configurers are registered before start; Handlers return errors), error-responses (Handler errors become problems). Hot paths: request dispatch, `Wrap`, Start/Shutdown.
2. **Lifecycle hardening**: config validation and defaults, `WithConfig` and option precedence, timeouts and body limit, Start failures, single-use Start, idempotent bounded Shutdown, shutdown hooks on every stop path. Satisfies server-lifecycle (all remaining except Lifecycle events are logged), error-responses (Oversized request bodies are refused). Hot paths: state machine, drain with forced close, hook runner.
3. **Routing completeness**: prefix joining, sub-groups, middleware ordering, `Mount`, conflict detection without panics, configurer panics. Satisfies route-registration (remaining). Hot paths: pattern join, registration recovery.
4. **Unmatched routes and panics**: 404/405 problems with `Allow`, panic recovery, late errors after commit, consumer prblm options and error hook. Satisfies error-responses (remaining). Hot paths: unmatched interception, recovery, committed-response tracking.
5. **Trace context and access log**: traceparent parse/generate, context accessor, `trace_id` problem member, default JSON stdout logger, one access record per request, request logger. Satisfies trace-context (all), error-responses (Problems carry the trace id), structured-logging (JSON lines by default; Request records carry trace correlation; One access record per request). Hot paths: traceparent parse, id generation, access record construction.
6. **Logging configuration and safety**: `LogConfig`, `AccessLogConfig`, `ServiceConfig` with their `With<Struct>` and individual options, LevelVar, AddSource correctness, own handler/logger, skip paths, redaction, truncation of every string attribute, failing output, service/build info, lifecycle and shutdown-hook events. Satisfies structured-logging (remaining), server-lifecycle (Lifecycle events are logged). Hot paths: handler wrapping, attribute truncation, write-failure counting.
7. **Triage error records**: error description, chain walk with limits, problem group, handler code location, panic stacks, fingerprint, build attributes, redactor. Satisfies triage-error-records (all). Hot paths: chain walk, fingerprint, stack capture, redactor recovery.

Each slice is releasable: after slice 1 a consumer can serve routes with problem errors; logs arrive in slice 5 because slice 1-4 errors are visible to the client and tests, and logging is easier to verify once trace ids exist.

## Decisions

### D1. `Start(ctx)` blocks; `Shutdown(ctx)` drains
`Start` binds, closes `Ready()`, serves, and on `ctx.Done()` calls an internal drain bounded by `ShutdownTimeout`, then returns nil. This fits `errgroup` and `signal.NotifyContext` usage. Alternative: non-blocking `Start` returning immediately - rejected, it forces every consumer to build their own wait and error propagation.
**Failure modes:** bind failure - returned before `Ready` closes; `Serve` returns an unexpected error - `Start` returns it wrapped; drain deadline exceeded - `http.Server.Close` forces connections closed, `Shutdown` returns `context.DeadlineExceeded`, `Start` still returns nil but logs `server.stopped` at `WARN` with `srvr.drain.forced`; concurrent `Start`/`Shutdown` - one mutex-guarded state machine (`new -> starting -> running -> stopping -> closed`), every transition tested under `-race`; a `Shutdown` that finds the server running claims the stop sequence under the same lock that read the state, so it never has to detect a concurrent stop that began in between; a listener passed with `WithListener` is owned by srvr once `New` returns a server (a failed `New` leaves it with the caller) - closed whenever the server closes (after serving, on a `Start` failure after leaving `new`, on `Shutdown` before `Start`), as `http.Server.Serve` does, while `Start(nil)` and `ErrServerStarted` do not close it and `ErrServerClosed` does not either (it was closed when the server closed); a `Start` context whose `Err()` is a typed nil or panics in `Error()` fails `Start` with that value, its text read through the guarded `errorText`; a typed-nil `WithListener` listener fails construction (`isNil`, like configurers and middleware); a listener whose `Addr()` returns nil or a typed nil or panics, or whose address's `String()` panics, fails `Start` with an error wrapping `ErrConfig` naming `Listener` through `fail` (logged, `AfterDrain` hooks, listener closed) - the address is read before the state lock is taken, under `recover`, never as a silent fallback (AGENTS rule 7). No srvr lock is held across a call into consumer code (listener methods, hooks, configurers, handlers, middleware, the redactor, log handlers, observers): the state mutex guards only srvr's own fields; the one other lock, the `sync.Once` making the listener's `Close` idempotent, guards no srvr state, so a caller waiting on it waits only for the same `Close` it would call itself.

### D2. `Register` validates eagerly, `Configure` runs at `Start`
`Register` returns an error for nil/typed-nil configurers and after start; `Configure` is called during `Start`, before binding, with panics recovered per configurer and ServeMux registration panics converted to `ErrRouteConfig` naming both patterns. Alternative: run `Configure` inside `Register` - rejected: ServeMux conflicts would then depend on registration order and panics would escape into consumer setup code. The user's sketch had `Register(conf)` with no result; returning `error` is a deliberate departure so misuse is never silent.
**Failure modes:** a configurer registers routes and then panics - the partially built mux is discarded, `Start` fails, the panic value's text read through the guarded `valueText` (a value whose `Error()` panics with itself would otherwise make `fmt` panic again); conflict detection relies on ServeMux's panic message for naming - srvr keeps its own registry of `(pattern, configurer type)` to name both sides without parsing the message.

### D3. `*srvr.Group` is a thin, ordered builder over ServeMux
Group holds prefix and a middleware slice snapshot; `Use` appends to the group's own slice (copy-on-create for sub-groups), so middleware applies only to routes registered after it, like gin and fiber. Routes are buffered as `(method, joined pattern, handler, middleware snapshot, code location)` and installed into the mux at the end of `Start`'s configure phase. Joining uses explicit string rules (collapse `//`, keep trailing `/`, keep wildcards) and then lets ServeMux validate the pattern by registering it under `recover`. Alternative: `path.Join` - rejected, it strips trailing slashes and so changes ServeMux subtree semantics.
`Mount` installs a method-less pattern and strips the group prefix (as `http.StripPrefix`) so plain handlers such as `http.FileServerFS` resolve paths relative to the mount point.
**Failure modes:** host-qualified or relative paths - rejected at configure time with the offending text; nil middleware or middleware returning nil - rejected at configure time; repeated wildcard names - surfaced from ServeMux's panic as `ErrRouteConfig`.

### D4. Error rendering through one prblm handler owned by the server
The server builds one `*prblm.Handler` from `consumer prblm options + srvr options` where srvr appends, last, its `OnError` and a `trace_id` enricher. srvr's `OnError` writes no log record: it stores the error, the problem sent and any `*prblm.PanicError` in the per-request state (D5), then calls the consumer's `WithErrorHook`. The access stage writes the single `http.request.failed` record from that state when the response finishes, so every request yields exactly one record. Handlers are wrapped with `prblm.Handler.Wrap`; the outer pipeline uses `Recover`. Because prblm's `OnError` is a single slot, a consumer who passes `prblm.OnError` inside `WithProblemOptions` is overridden by srvr's hook; godoc points them to `WithErrorHook`. Alternative: let the consumer's `OnError` win - rejected, it silently disables error logging, which is the triage path.
**Failure modes:** invalid prblm option panics in `NewHandler` - recovered in `srvr.New` and returned as `ErrConfig`, the panic value's text read through `valueText`; consumer hook panics - recovered by srvr before prblm sees it; prblm hook receives notes about rendering mistakes (`ErrInvalidStatus`, `ErrInvalidType`, `ErrUndocumentedType`, `ErrEncoding`, `ErrShadowedDocumentation`) - dropped, not logged and never dereferenced (a `srvr.problem.note` event is an open `unassigned` carry-over in `notes.md`); a `*PanicError` with a nil problem (a panic after the response started, on a broken connection or while answering) is a failure, not a note; `OnError` called more than once for one request - the state keeps the first failure that has a problem and drops later ones, while a failure without a problem (such a panic) is kept only until a failure with a problem arrives, which replaces it (documented on `recordFailure`); a failed record is never suppressed by `AccessLogConfig`, and a failure after the response started is logged at the higher of the level of the status sent and of the status it would have been answered with (a panic at `ERROR`; a late 4xx after `2xx` at `WARN`, after `5xx` at `ERROR`); `http.response.status_code` is the final status the client receives, `200` when only a `1xx` was written; `OnError` never called although the status is 5xx (a handler wrote `500` itself) - logged as `http.request.completed`, no triage attributes invented. Unmatched 404/405 are rendered by srvr itself (D5) and recorded in the same state, so they log `http.request.failed` at `WARN` on every engine.

### D5. 404/405 by interception of ServeMux's fallback
The pipeline asks the mux for the handler (`mux.Handler(r)`); when the returned pattern is empty, the request is unmatched. The fallback handler is run against a recording writer that captures status and `Allow`; srvr then renders `prblm.ErrNotFound` or a 405 problem, copying `Allow`. Alternative: register catch-all `/` - rejected, it hides 405 information and collides with consumer `/` routes.
**Failure modes:** for a redirect (307 on Go 1.27) `mux.Handler` reports the pattern that will match after the redirect - `/dir/` for both `/dir` (trailing slash) and `/a/../dir/` (non-canonical path) - and reports an empty pattern only for requests no route matches (404, 405) and for a redirect whose target is also unmatched (`//nope` -> `/nope`, verified on Go 1.27.4) - so an empty pattern is not proof of 404/405: only recorded 404 and 405 statuses are converted, other statuses pass through unchanged; matched requests are dispatched through `mux.ServeHTTP`, never by calling the handler `mux.Handler` returned, because that leaves `r.Pattern` and `r.PathValue` empty; `r.Pattern` is set only on the request value the mux receives, so an outer middleware that passed down a `WithContext` copy reads the route from a shared per-request holder, not from its own `r`; future Go versions changing fallback behaviour - pinned by an Examples-driven test on every Go version in CI.

### D6. Trace context is srvr's own, OpenTelemetry-free
A small internal package parses `traceparent` per W3C level 1 (strict lowercase hex, version rules, single header, length cap) and generates ids with `crypto/rand`. The request context carries a `srvr.Trace{TraceID, SpanID, ParentSpanID, Sampled}`. The next-but-one change lets `otelsrvr` replace the source with the active span. Alternative: depend on the OTel API for `trace.SpanContext` - rejected by the dependency rule for the core module.
**Failure modes:** `crypto/rand` failure - Go 1.24+ `crypto/rand.Read` never returns an error and crashes irrecoverably on failure, documented; duplicate headers - treated as invalid (new trace).

### D7. Logging pipeline: wrapper handler around the configured slog handler
`srvr.New` resolves a base `slog.Handler` (consumer's, or JSON/text to the output with level and AddSource), then wraps it in one srvr handler that (a) adds `trace_id`/`span_id` from the context, (b) truncates every string attribute, (c) recovers panics and counts errors in every call it makes to the base handler - `Enabled`, the replayed `WithAttrs`/`WithGroup` and `Handle` - skipping the record on a failure, so a faulty consumer handler never reaches the response. Failures go to one process-wide counter read with `LogWriteErrors()`, shared by every server in the process (a per-server counter would need the server at the call site, which `slog.Default()` loggers do not have).
Correlation and groups: a correlation key added inside `Handle` with `Record.AddAttrs` lands inside any open group (`{"db":{"trace_id":..}}`, proven by the planning probe `probes/xgroup`). So the srvr handler does not forward `WithGroup`/`WithAttrs` to the base handler; it records them as an ordered list of steps (attributes already truncated) and, in `Handle`, builds `base.WithAttrs(trace_id, span_id[, srvr.attr.truncated])` and then replays the steps before calling `Handle`. With no steps the base handler is used directly (fast path). Alternatives: pre-binding correlation per request - rejected, it misses `slog.Default()` loggers derived before the request; accepting nested keys - rejected, the log schema promises a top-level `trace_id`. Cost: replay rebuilds the handler chain per grouped record (built-in handlers pre-format on `WithAttrs`); a benchmark of grouped versus ungrouped records is recorded in `notes.md`, and caching the replayed handler per trace is the refactoring if it matters.
Truncation: the wrapper first calls `Value.Resolve()` on every attribute (slog hands `Handle` a `KindLogValuer` value unresolved - planning probe `probes/audit2/core2` `TestKinds`), then cuts every `slog.KindString` value, every `KindAny` value implementing `error` (its `Error()` text read through the same guarded formatting as triage records - `<nil T>` for a typed nil, `<panic in Error(): T>` for a panicking `Error()` - and written as a string) and the record `msg`, in the record, in recorded `With` steps and inside groups, to `MaxAttrBytes` (default 1024; 0 = default; negative disables) at a UTF-8 boundary plus `…[truncated]`, and the record gets top-level `srvr.attr.truncated` `true`. Only the records srvr builds itself give `exception.message` (8 KiB) and `exception.stacktrace` (32 KiB) larger limits; srvr marks them internally, so a consumer attribute named `exception.message` gets `MaxAttrBytes` like any other. It is done in the wrapper, not `HandlerOptions.ReplaceAttr`, because `ReplaceAttr` exists only on slog's built-in handlers and srvr does not own a consumer's handler. Other `Any` values (structs, slices, maps) are not truncated - cutting them would need encoding them first; their size is the caller's responsibility (documented). Access records are built with `slog.Record` and `Handler.Handle` directly with PC 0, so they never carry `source`. Config text fields are strings parsed at construction (`slog.Level.UnmarshalText`, format enum) so errors name the field. Alternative: typed `slog.Level` fields in the config struct - rejected, a decode error from the loader would not name srvr's field and empty would not mean default.
**Failure modes:** consumer handler blocks - not mitigated (synchronous by design; documented on `WithLogHandler` and `WithLogger`, async would lose records on crash); `MaxAttrBytes` negative - nothing is cut, but srvr's own `exception.*` text and `error` values still reach the base handler as plain strings (a consumer handler never sees srvr's internal text type, and never formats a hostile `error` itself); `WithAttrs`/`WithGroup` must keep correlation top-level - tested with the Grouped loggers rows, including empty group names and `slog.Default()` after `WithSetDefaultLogger()`; `slog.SetDefault` is only done with the explicit `WithSetDefaultLogger()` opt-in, never implicitly.

### D8. Triage record builder
At failure, one builder produces the `http.request.failed` record: walk the chain breadth-first through `Unwrap() error` and `Unwrap() []error` with depth and count caps and per-call `recover`; type names via `%T`; message via guarded `Error()`, the consumer redactor and an 8 KiB cap, built by one helper that srvr's lifecycle records use too (D9); fingerprint = first 8 bytes of SHA-256 over `method|route|types...` (panics: `method|route|panic type|top application frame`, the first frame after `panic` that is not in `runtime`, `runtime/debug`, prblm or srvr - the stack prblm captures starts with `runtime/debug.Stack` and `prblm.(*Handler).recoverPanic`), hex-encoded; handler location resolved at registration with `runtime.FuncForPC` on the handler's code pointer (method values resolve to the `-fm` wrapper and are normalised); panic stack from the `*prblm.PanicError` the hook receives (`Stack`, captured with `debug.Stack()` inside recovery), capped at 32 KiB; `exception.message` for a panic is formatted from `PanicError.Value`, not `PanicError.Error()`, which prefixes `prblm: recovered panic: `. For a panic `error.type` is the constant `panic` and the value's Go type goes to the semconv key `exception.type`, so `error.type` means "what kind of failure" with one value per kind on every signal (otel-observability uses `panic` for metrics too); for a returned error `error.type` is the innermost Go type in logs. Alternative: capture stacks for all errors - deferred (`unassigned` carry-over), Go errors carry no stack and capturing at return time adds cost without pointing at the origin.
**Failure modes:** `-fm` suffix and generic instantiation names - normalised and tested; unknown PC (assembly, reflect-made funcs) - attributes omitted, never invented; redactor panic - attribute replaced with `[redaction failed]`; redactor blocks - not mitigated, it runs synchronously in the request's access stage or the lifecycle call (documented on `WithErrorRedactor`). Formatting rule for every consumer value (errors, panic values, listener addresses, context errors): srvr reads its text only through `errorText` or `valueText` (which reads an `error` value through `errorText`, so a panic value that is an error shows as `<panic in Error(): T>`, like a logged error), never by handing the bare value to a `fmt` verb, because `fmt` contains a panicking `Error()`/`String()` only one level deep - it formats the panic value, and a value whose `Error()` panics with itself makes it panic again (`fatal error: panic while printing panic value` on a goroutine srvr owns). Errors srvr builds around consumer errors wrap them in `guardedError` (its `Error()` is `errorText`, its `Unwrap` keeps `errors.Is` working), so `fmt.Errorf` with `%w` stays safe; `configError` reads its value through `valueText` itself, so no caller has to.

### D9. Shutdown hooks owned by the core
`WithShutdownHook(phase ShutdownPhase, fn func(context.Context) error)` with phases `BeforeDrain` and `AfterDrain`. Later changes (otel exporter flush, scrty session signals) and consumers (database pools) use this one mechanism. Stop sequence, shared by every stop path (`Start`'s context ending, `Shutdown`, `Start` failing after construction, `Shutdown` before `Start`): close the listener -> `BeforeDrain` hooks in registration order, with the drain context (they consume `ShutdownTimeout`) -> drain -> `AfterDrain` hooks in registration order, with a fresh context bounded by `ShutdownHookTimeout` (default 5s; negative = unbounded), so a slow drain cannot starve an exporter flush. A `sync.Once` guards the sequence; the state machine makes concurrent stop calls wait for it. A never-started server or a failed bind skips the drain and `BeforeDrain` hooks. Each hook runs under `recover` in its own goroutine; srvr stops waiting at the budget (a hook ignoring its context leaks its goroutine, documented). A hook error's text is read through the guarded `errorText` (`<nil T>` for a typed nil, `<panic in Error(): T>` for a panicking `Error()`), because `runHooks` runs in the stopping caller's goroutine: an unguarded `Error()` would panic out of `Start` or `Shutdown` before the sequence closes the server, and every later `Shutdown` would wait forever. A hook's panic value is formatted with `valueText`; the error joined into the stopping call's result wraps `ErrShutdownHook` and the hook's error inside a `guardedError`, and an abandoned hook's error wraps the hook context's `Err()` (from the consumer's `Shutdown` context for `BeforeDrain`) the same guarded way. Failures are logged as `server.shutdown_hook.failed` (`WARN`, `srvr.shutdown_hook.phase`, `srvr.shutdown_hook.index`, `code.function.name`, `exception.message`) and joined into the stopping call's error, wrapping `ErrShutdownHook`. The `exception.message` of `server.shutdown_hook.failed` and `server.failed` is built by the same helper as a request failure record's (D8: guarded text, then the `WithErrorRedactor` redactor with `[redaction failed]` for a panicking redactor, then the 8 KiB limit, marked as srvr's own text so `MaxAttrBytes` does not cut it again), so no call site builds the attribute by hand: hook errors and `Start` context errors are consumer text (a database close error may carry a connection string). Alternatives: hooks only on `Shutdown` - rejected, the common `signal.NotifyContext` pattern never calls it; `http.Server.RegisterOnShutdown` - rejected, it runs hooks concurrently, without order or result.
Which `Start` failures stop: every failure after the server leaves its initial state - configure failure or panic, route conflict or route-check failure, bind failure, a context already done - runs the `AfterDrain` hooks once (nothing was served, so no drain and no `BeforeDrain`); `Start(nil)` and the misuse errors `ErrServerStarted` and `ErrServerClosed` change no state and run no hooks, so a second `Start` never touches a running server's hooks. A `BeforeDrain` hook that blocks is abandoned at the drain deadline; the drain then runs with the spent budget (forced close) and `AfterDrain` hooks still get their own budget.
**Failure modes:** hook calls `Shutdown` - that call waits for the running sequence, which stops waiting for the hook at its budget, so the inner call returns `nil` after the stop finishes and the outer call reports the hook as timed out (with a negative, unbounded budget it would deadlock - documented), tested by the Blocking and re-entrant hooks rows; hook panics with `nil` - reported as a panic; `AfterDrain` budget extends past the caller's `Shutdown` deadline - documented (keep `ShutdownTimeout + ShutdownHookTimeout` under the platform grace period, 20s of Kubernetes' 30s by default).

### D10. Options and config structs compose in argument order
Every config struct has a `With<Struct>` option (`WithConfig`, `WithLogConfig`, `WithAccessLogConfig`, `WithServiceConfig`, `WithTraceConfig`) and each field an individual option (`WithAddr`, `WithLogLevel`, `WithLogAddSource`, `WithLogMaxAttrBytes`, `WithAccessLogSkipPaths`, `WithAccessLogDisabled`, `WithAccessLogIncludePath`/`Query`/`ClientAddress`, `WithServiceName`/`Version`/`Environment`, `WithIgnoreIncomingTraceContext`, ...). Options mutate one settings value in argument order; a `With<Struct>` option overwrites every field of its struct (zero = default), so `WithAddr(":7070"), WithConfig(Config{})` listens on `:8080`. `Config` holds only the server fields (address, timeouts, limits, `ShutdownHookTimeout`); `LogConfig`, `AccessLogConfig`, `ServiceConfig` and `TraceConfig` are separate top-level structs, never nested in `Config`, each set by its own `With<Struct>`. A `With<Struct>` sets every field of its struct, including structs nested inside it (for example a later change's `LogConfig.DebugBuffer`), so it resets anything an earlier option set there. Validation runs once after all options, so errors name the final value. Alternative: struct-then-options precedence regardless of order - rejected, it is surprising and hard to explain in godoc.

## Defaults

| Behaviour | Default | Why | Override |
|-----------|---------|-----|----------|
| Address | `:8080` | conventional container port | `WithAddr`, `Config.Addr`, `WithListener` |
| ReadHeaderTimeout | 10s | Slowloris protection | option / config; negative disables |
| Read/Write timeouts | 60s / 60s | bounded resource use; long enough for typical APIs | option / config; negative disables (streaming) |
| IdleTimeout | 120s | keep-alive reuse without leaking idle conns | option / config |
| MaxHeaderBytes | 1 MiB | net/http default made explicit | option / config |
| Request body limit | 4 MiB | refuse accidental or hostile large bodies | option / config; negative disables |
| Shutdown drain | 15s | fits a 30s Kubernetes grace period | option / config |
| Shutdown hook budget (`AfterDrain`) | 5s | exporter flush without starving on a slow drain; 15s + 5s fits 30s | `Config.ShutdownHookTimeout`; negative = unbounded |
| String attribute limit | 1024 bytes, `…[truncated]` | one hostile or careless value cannot flood the log pipeline | `WithLogMaxAttrBytes`, `LogConfig.MaxAttrBytes`; negative disables |
| Error format | prblm JSON, `trace_id` member | one format, correlatable | `WithProblemOptions`, `WithErrorHook` |
| Log output | JSON to stdout, INFO, no source | agents read stdout; least noise | `LogConfig`, options, own handler |
| Access log | on; completed records below 500 suppressible, failed records never | errors are always the triage record | `AccessLogConfig` |
| Privacy | no bodies, credentials, query, path, client address | logs may reach third-party tools | `IncludePath`, `IncludeQuery`, `IncludeClientAddress` |
| Incoming traceparent | honoured | standard W3C behaviour | `IgnoreIncomingTraceContext` |
| Service info | `unknown_service:<exe>`, build version | OTel convention | `ServiceConfig` |

## Hot Paths

- Per request: trace context (parse, generate), access-log wrapper (status/bytes recording writer, commit tracking), recovery, mux dispatch or unmatched interception, handler wrap, prblm render, `OnError` -> triage record -> log write.
- Error branches: invalid traceparent, handler error, panic (including `http.ErrAbortHandler`), late error after commit, consumer hook panic, log handler error/panic, chain-walk limits, redactor panic.
- Lifecycle: configure phase (join, conflict, configurer panic), bind, ready, drain, forced close, every illegal transition.

## Risks / Trade-offs

- [prblm `OnError` is single-slot] -> srvr owns it and exposes `WithErrorHook`; one `unassigned` carry-over asks prblm for composable hooks and an exported status-only sentinel (`notes.md`).
- [ServeMux fallback interception depends on stdlib behaviour] -> Examples-driven tests run on every supported Go version.
- [Synchronous logging can slow requests when stdout blocks] -> documented; per-request buffering change does not change this.
- [Log schema becomes a public contract] -> keys centralised in one internal file with a golden-record test pinning every event's keys; `srvr.log.schema` `1` on every record srvr writes itself (not on consumer records). Adding a key keeps the version; renaming or removing a key, or changing a key's meaning or value type, bumps it - the golden test fails on such a change until the version is bumped. Later changes (otel-observability, scrty-integration, triage-debug-buffer) only add keys.
- [Group replay costs allocations per grouped record] -> fast path for ungrouped loggers; benchmark recorded in `notes.md`; per-trace caching as the refactoring if the cost matters.
- [Handler code location for closures is less helpful] -> function literal names (`main.routes.func1`) still locate the file and line.
- [Pre-1.0 prblm] -> pin the minor version; consolidation group of each change re-checks it.
- [`http.Server` treats a zero `ReadHeaderTimeout` or `IdleTimeout` as "use `ReadTimeout`"] -> srvr passes a disabled timeout to `http.Server` as a negative value, never zero; covered by the Effective limits rows.
- [`http.Server.Shutdown` does not wait for hijacked connections (WebSockets)] -> documented as a limitation of this change; `http.Server.RegisterOnShutdown` is the stdlib mechanism a later change can expose.
- [Kubernetes removes endpoints asynchronously after SIGTERM, so requests can still arrive while draining] -> documented: use a `preStop` sleep or keep `ShutdownTimeout` plus that delay under `terminationGracePeriodSeconds` (default 30s).

## Migration Plan

New library; nothing to migrate. Release as `v0.1.0` of `github.com/kartaladev/srvr` after slice 7.
